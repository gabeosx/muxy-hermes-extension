# Goal

Make a card created in Muxy usable by the real Hermes Kanban dispatcher and keep the open board synchronized with worker-driven lifecycle changes.

# Verified baseline

- An isolated Hermes Agent 0.20.2 run proved `ready → running → done` and `ready → running → blocked`, each with one attached Kanban run and the expected outcome.
- The existing Muxy form creates unassigned title-only cards, so those cards cannot be dispatched without another surface assigning them.
- The existing Muxy board reloads only on explicit user actions, so Hermes-driven transitions remain stale until Refresh is clicked.

# Tasks

1. Extend the Kanban client and project-board form with an assignee and task instructions, preserving scratch-workspace and privacy boundaries. Add a bounded serialized refresh loop while the board tab is open so Hermes dispatcher/worker status changes appear without user intervention.
2. Update automated contracts and README copy to describe the real Hermes lifecycle accurately. Run the full test/build/validation gates and repeat the isolated real-Hermes lifecycle proof using `KanbanClient.createTask` rather than a direct API bypass.

# Acceptance

- A user can create a card with a Hermes assignee and task instructions from Muxy.
- Promoting that card to Ready allows Hermes to claim it; the open Muxy board reflects Running and the worker-selected terminal status automatically.
- Standalone requests from the Agent panel remain clearly distinguished from Kanban-dispatched worker runs.
- Refresh polling is serialized, stops on release/session loss, and never persists or displays task bodies, paths, credentials, or run identifiers.
- Unit tests, build, distribution validation, complete validation, and the isolated real-Hermes completion/blocked proof pass.
